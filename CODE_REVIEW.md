## 1. Архитектура и логика работы

### 1.1 Общий поток работы

Проект реализует подход **Learning-to-Optimize (L2O)** для оптимизации гиперпараметров с использованием Reinforcement Learning. Ключевая идея: RL-агент учится **процессу выбора** гиперпараметров, а не напрямую оптимизирует их значения.

**Основной workflow:**
```
YAML Config → Backend → Environment → RL Agent → Обучение → Оптимизированная стратегия
```

### 1.2 Ключевые компоненты

#### Backends (Движки оценки)
- **OptimizationBenchmarkBackend**: Тестирование на эталонных функциях (sphere, rastrigin, rosenbrock и т.д.)
- **DummyBackend**: Простой тестовый backend для отладки
- **RealTrainingBackend**: Полноценный backend для реального обучения ML-моделей
- Все реализуют интерфейс `EvaluationBackend.evaluate(config) -> float`

#### Environments (RL-среды)
Проект предоставляет несколько вариантов формулировки RL-задачи:

1. **CyclicPipelineEnv** (основная среда):
   - Циклический выбор гиперпараметров по одному
   - Поддерживает дискретные и непрерывные действия
   - Reward modes: `per_step` (плотная награда) и `per_cycle` (разреженная)
   - Поддержка различных размеров шагов
   - Адаптивный штраф за размер шага

2. **ContinuousPipelineEnv**: Последовательный выбор всех гиперпараметров за один эпизод
3. **DiscretizedPipelineEnv**: Дискретизированные непрерывные действия
4. **DiscretePipelineEnv**: Нативная дискретная среда с маскированием
5. **StrategyEnv**: Среда, где агент сам выбирает порядок настройки параметров

#### Core System
- **Factory Pattern**: Система регистрации и создания компонентов через реестры
- **Builder Pattern**: Для построения оптимизаторов (Adam, SGD)
- **Registration System**: Инициализация через `initialize_framework()`

### 1.3 Логика обучения

1. **Инициализация**:
   - Загрузка YAML конфигурации
   - Создание backend через factory
   - Генерация пространства гиперпараметров
   - Создание среды с backend и hp_space

2. **Обучение агента**:
   - RL-агент (PPO, SAC, TD3 и т.д.) обучается на среде
   - Среда преобразует действия агента в значения гиперпараметров
   - При каждом изменении вызывается `backend.evaluate(config)` для получения reward

3. **Transfer Learning**:
   - Обучение на задаче A (например, Rastrigin)
   - Zero-shot оценка на задаче B (например, Sphere)
   - Опциональное few-shot дообучение

### 2.2 Environments

#### CyclicPipelineEnv (основная среда) ⭐
**Сильные стороны:**
- Очень гибкая реализация с множеством параметров
- Поддержка двух режимов reward (per_step/per_cycle)
- Поддержка дискретных и непрерывных действий
- Адаптивный штраф за размер шага
- Сохранение истории (prev_cycle_indices)

**Логика reward (per_step режим):**
```python
diff = new_metric - current_metric
scale_factor = 100.0
if diff >= 0:
    reward = math.log(1 + diff * scale_factor)
else:
    reward = -math.log(1 + abs(diff) * scale_factor)
```
- Использует логарифмическое масштабирование
- Бонус +1.0 за новое лучшее значение
- Адаптивный штраф за размер шага (опционально)

**Проблемы/Вопросы:**
1. **Захардкоженный scale_factor = 100.0**: Желательно сделать настраиваемым
2. **Оценка при reset()**: Выполняется полная оценка при сбросе, что может быть дорого для реальных backends
3. **Логарифмическое масштабирование**: Может вызывать численные проблемы при очень малых diff
4. **One-hot кодирование**: Для большого количества параметров может быть неэффективным

**Проблема с continuous действиями:**
- В строке 190: `if new_idx != old_idx or self.action_type == "continuous":` - условие всегда True для continuous, что может приводить к избыточным оценкам

## 5. Логика работы: детальный анализ

### 5.1 Циклический процесс выбора (CyclicPipelineEnv)

**Процесс:**
1. Агент циклически выбирает один гиперпараметр за раз
2. Для каждого параметра агент выбирает действие (уменьшить/увеличить/остаться)
3. При каждом изменении:
   - Вычисляется новая конфигурация
   - Вызывается `backend.evaluate(config)`
   - Вычисляется reward на основе улучшения
   - Обновляется лучшее значение

**Циклы:**
- После прохода по всем параметрам начинается новый цикл
- Предыдущие значения сохраняются в `prev_cycle_indices`
- Это позволяет агенту видеть историю

**Награда:**
- **per_step**: Плотная награда после каждого шага
  - Логарифмическое масштабирование разности метрик
  - Бонус за лучшее значение
  - Штраф за размер шага (опционально)
- **per_cycle**: Разреженная награда после завершения цикла
  - Награда только за улучшение за весь цикл

### 5.2 Transfer Learning

**Процесс:**
1. Обучение на задаче A (например, Rastrigin функция)
2. Zero-shot оценка на задаче B (Sphere)
   - Модель загружается
   - Тестируется без обучения
3. Few-shot дообучение (опционально):
   - Увеличение exploration (ent_coef)
   - Увеличение learning rate
   - Дообучение на небольшом количестве шагов

**Важно:**
- Параметры среды должны совпадать (num_bins, step_sizes, dimensions)
- Менять можно только функцию и границы

**Проблемы:**
- Переобучение на исходной задаче может ухудшить перенос
- Рекомендуется использовать больше exploration boost (2.0-3.0)

### 5.3 Преобразование действий в гиперпараметры

**Дискретные действия:**
```
Действие → размер шага → изменение индекса → нормализация → денормализация → значение
```

**Непрерывные действия:**
```
[0, 1] → целевой индекс (с ограничением шага) → нормализация → денормализация → значение
```

**Логарифмическая шкала:**
- Для параметров с `log: True` используется логарифмическое масштабирование
- Это важно для параметров с широким диапазоном (например, learning rate)
