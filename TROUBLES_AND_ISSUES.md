# Отчет о проблемах и неудачных решениях

## Краткое резюме

Этот документ выявляет архитектурные проблемы, проблемы проектирования, проблемы качества кода и потенциальные улучшения для проекта HPO_RL. Анализ основан на обзоре кода, комментариях и структурном анализе кодовой базы.

**Важное примечание**: При анализе учитывалось, что комментарии в README и коде могут быть устаревшими или основанными на неправильном понимании. Фокус сделан на реальных проблемах кода и архитектуры, а не на философских вопросах, которые могут быть отражены в устаревших комментариях.

## Критические проблемы

### 1. Неясность формулировки задачи в документации

**Проблема**: Комментарии в README могут вводить в заблуждение относительно правильности подхода.

**Местоположение**: `README.md` строки 25-28

**Описание**: 
README содержит комментарий, который может быть неправильно истолкован. На самом деле, подход Learning-to-Optimize (L2O) - оптимизация процесса выбора гиперпараметров, а не самих гиперпараметров - является правильным выбором по следующим причинам:
- Прямая оптимизация гиперпараметров вычислительно слишком дорога в текущих средах
- L2O позволяет лучше переносить знания между задачами
- Модели, оптимизирующие гиперпараметры напрямую, просто возвращают оптимальные гиперпараметры для модели, на которой они обучались, что плохо переносится

**Влияние**: 
- Неясность в документации может привести к неправильному пониманию архитектурных решений
- Разработчики могут попытаться изменить подход, думая, что это ошибка

**Рекомендация**: 
- Обновить README, чтобы четко объяснить, почему L2O является правильным подходом
- Документировать преимущества оптимизации процесса оптимизации для переноса знаний
- Удалить или переформулировать вводящие в заблуждение комментарии

### 2. Разные интерфейсы инициализации Backend (не проблема)

**Статус**: Это нормальный дизайн, не проблема.

**Местоположение**: `hpo_rl/backends/` (все файлы)

**Описание**:
Разные бэкенды имеют разные параметры инициализации, что является нормальным и ожидаемым:
- `OptimizationBenchmarkBackend`: Принимает function_name, dimensions и т.д. - параметры для эталонных функций
- `DummyBackend`: Принимает словарь optimum - параметры для тестового бэкенда
- `RealTrainingBackend`: Принимает model_names, train_data и т.д. - параметры для реального обучения
- `TableBackend`: Принимает csv_path, param_names - параметры для табличного бэкенда

**Важно**: Все бэкенды реализуют общий интерфейс `EvaluationBackend` с методом `evaluate(config: Dict[str, Any]) -> float`, что является правильным применением полиморфизма.

**Вывод**: Различие в параметрах инициализации - это нормально, так как разные бэкенды имеют разные требования. Главное - единый интерфейс `evaluate`, который и обеспечивает возможность замены бэкендов.

**Местоположения**: Несколько сред

**Проблемы**:

**`hpo_rl/environments/cycle_move_pipeline.py` строки 95-99**:

**Рекомендация**:
- Нормализовать награды для разных backends
- Сделать масштабирование награды настраиваемым
- Рассмотреть техники нормализации награды
